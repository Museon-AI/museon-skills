# 如何区分阻塞、交给用户并验收

## 验证入口不能代表具体验证类型

`Confirm you're human` 只是入口。已实际观察到点击 Continue 后出现图片中的扭曲字符验证码，而不是人脸或邮箱码；仅凭入口文案不能将整批设备判为同一种验证。

在获准的查看范围内打开具体要求，记录页面原文、平台、阶段与必要截图；不要识别、核对或自动提交 CAPTCHA。用户完成验证后再接续正常流程。

| 实际页面 | 如何处理 |
| --- | --- |
| 本次邮箱验证码 | 正常账号确认流程；核对邮箱、发件方和本次请求时间，取得本人的有效码后继续 |
| 图片字符、选图或其他 CAPTCHA | 截图说明类型，交给用户手动完成；不代识别、核对、填写或提交 |
| 人脸 / 自拍视频 / 证件 | 明确记录要求，交给本人完成，不用头像资料伪造或替代 |
| 强制手机号 | 单独记手机号要求；不将其误记为图片验证码 |
| HTTP 429 / 网络失败 / 空白页 | 技术待处理，不代表账号注册失败或人工验证 |
| `Your account was banned` / 无验证选项的停用 | 记录封禁/停用，不把它归到 CAPTCHA |

停用页面若仍明确要求确认本人，应按实际下一步分类，不能只匹配 `suspended` 就归为封禁。备注中“未要求自拍/人脸”是否定证据，不能通过关键词扫描计为人脸案例；历史邮箱验证码也不能证明当前人机入口是邮箱验证。

## 单台云机的用户直连链接

用户要手动接管时，给该台手机的临时远程链接，不是 GeeLark 首页、登录页或一张截图。

从[官方启动接口](https://github.com/GeeLark/geelark-openapi/blob/main/docs/en/Cloud%20Phone%20API/Cloud%20Phone%20Management/Start_cloud_phone.md) `phone/start` 的 `successDetails` 中，按本台 `id` 取对应 `url`；官方说明该 URL 可在浏览器直接访问手机。检查它属于本台设备，并在页面就绪后交接。URL 可能位于 `phone.geelark.cn`，不能假定必须是 `.com` 域。

远程 URL 带临时 token：只在用户明确要求的私有交接中提供，不提交仓库、不放公开报告、不送搜索引擎核验。链接失效就从同台设备获取新的官方 URL，不手拼 token、沿用旧批链接或混入长期 API key。

交接时报告设备编号、当前页面及是否开机，并保留唯一拥有者和必要租约。当前页面未就绪就如实说还未就绪；用户手动操作期间不抢输入。用户结束后检查后续实际状态，按约定回填和关机。

## 常见故障的已验证判断方法

- **Lite 入口或最终提交卡住**：已有账号先核实，再转同机官方网页。网页已验证可成功；这不证明所有 Android 版本或地区的 Lite 都不可用。
- **输入截断**：有过快速 shell 输入丢字符的案例。提交前核实邮箱完整性，必要时放慢输入；不要因错误账号查询结果改绑资料。
- **资料或简介没保存**：以保存后重新打开的内容为准。某个表情搜不到时，可以检查正常键盘/剪贴板能力，不先下版本或地区结论。
- **429**：识别服务端还是代理返回，遵守 `Retry-After` 或服务端提示；没有状态变化时不连续刷新、发码或提交。
- **Play 附加资源 / 登录回跳**：核实安装来源、版本和实际更新按钮。地区不可用、组件获取失败、Google 授权 HTTP 错误分别记录；不把它们直接叫封禁。
- **运行环境 `Operation not permitted`**：连接前失败且没有 API 响应时，先核对当前实际网络/执行器状态。配置显示 unrestricted 与连接真正可用不是同一事实；记录实测，不武断称服务没权限。按明确规则修复或正常交接，不能用换通道绕过实际访问拒绝。
- **技能/命令缺失**：使用交接的可读材料及当前获准 API。只有真实网络、服务身份或工具拒绝，才记成对应阻塞。

## 最后检查什么

1. **归属**：本批设备数量、当前会话数量与分配唯一性；每套邮箱、资料包、四个平台行一致。重复会话历史不等于重复账号，但同一时刻只能有一个操作者。
2. **结果**：成功字段齐全；受阻有具体原因和阶段；技术未解决有剩余步骤。登录成功不等于完整资料已验收，密码已保存不等于密码已验证。
3. **凭据**：确认字段来源、提交值保存及回读一致，不输出密码；平台密码与邮箱密码疑似混用时回到执行者核实。
4. **资料和设备**：资料绑定/完成状态符合当前指南，所有结束设备确实关机；手动交接者明确单列，不能宣称整批已关机。

协调器发现异常时让原执行者修复自己的原行并回读，避免另一个 Agent 批量覆盖结果。

## 用户能看懂的汇报

先写操作了多少**套账号 / 台设备**，再列各平台的 `通过数 / 本批套数` 和通过率。分母按用户定义的本批范围确定：批次外人工操作设备单列，批内由人工接续的设备保留在分母；重复重试不重复计数，会话数和四个平台明细总数也不是账号套数。

主要未通过原因按数量及占未通过记录比例从高到低直接展示；各平台明细折叠下钻。验证类型未查明的保留“未确认”，抽查一台不能外推整批。把网页兜底等经验证的流程转折写清，但不要用整套四平台全通过率为零作为报告主标题。

飞书卡片按已确认的用户私聊或群聊投递，发送后回读消息。汇报任务数、成功数、仍受阻数、记录位置、检查范围和未验证项；未获消息投递授权时先在当前对话交付可审阅内容。
