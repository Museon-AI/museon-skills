# 如何分派、接续和回收云任务

## 先验证云环境能执行

用当前可用工具发现云环境和命令 schema。Codex 桌面已验证的路径是：`list_cloud_environments` 取得可运行的配置，`create_thread` 的 `target.type=codexCloud` 创建用户明确要求的独立云会话；`environmentConfigId` 必须来自本批实际配置。模型和推理档位沿用用户配置，除非本批指定。

云端就绪检查包括凭据状态、目标服务连通性、指定设备只读查询、SOP 与原表可读，以及回填所需身份的权限。读权限不能证明写权限；用当前接口权限说明或本批授权的实际写入及回读验证。报告具体响应，而不是以“没装 CLI”或一次旧接口 scope 错误结束。

配置 ID 不是运行实例 ID。同一配置可用于多个会话；本批要求每套独立运行环境时，还需核实实际实例与工作目录隔离，不能仅凭会话 ID 不同就声称环境隔离已验收。

历史 CLI Cloud 启动曾落到不同配置、只读实例；这不能推出所有版本都不支持 Cloud。使用 CLI 前先读当前 `--help`，再核实启动实例的实际配置及权限。不要把桌面云配置 ID、CLI 参数与项目 ID 混用。

## 每套只有一个活跃拥有者

在本批私有任务台账中保存：

| 字段 | 用途 |
| --- | --- |
| 设备编号、`phone_id` | 编号用于找设备，ID 用于接口调用 |
| `profile_id`、四行 `record_id` 与平台 | 固定资料及回填归属 |
| 当前 `thread_id`、历史会话 ID | 保留接手关系，避免重复派发 |
| 分配、接受、执行、回填待验、已验收、受阻状态 | 区分会话状态与业务结果 |
| 最近检查时间、进度 cursor、剩余步骤 | 增量检查与恢复 |

密码和访问 token 留在原凭据来源，台账只保存引用。创建成功后先持久化新会话 ID，再回读状态；避免工具回读失败后重复创建。

## 派发与自动补位

1. 从原表确认本批待办及当前占用，先盘点已有云会话，去重后分配。候选号不存在或已占用时，仅从本批授权的空闲范围补选。
2. 原子领取资料并回读绑定，再交给该套唯一执行者。替换会话不重新领取资料。
3. 将当前生效的 skill 必要正文或文件随任务送入云端。本机绝对路径不代表云端可读；动态 SOP 仍应从原文读取。
4. 用 `read_thread` 确认新 turn 进入 `inProgress`。创建/发送成功只表示请求被接受，不等于业务已经运行。
5. 用 `wait_threads` 的 cursor 增量回收；每次最多按当前 schema 支持的目标数分组。只返回部分目标是可能的，未返回者继续保留占位。
6. 执行者完成本套回填、回读和设备收尾后，再补下一套；失败待诊断的会话不因显示 idle 就直接释放业务归属。

并发是本批参数：例如用户批准上限 25，就保持最多 25 套活跃任务。按已回收任务补位，不把整批账号塞进一个环境，也不自行扩大并发。

### 精简的执行交接

下面是字段模板，展开为可读任务正文；资料值从受控来源读取：

```text
只处理设备 {device_no}，phone_id={phone_id}；资料 {profile_id} 已绑定。
四行记录：{platform: record_id}。SOP：{sop_url}。
本套独占一个云会话；沿用原设备、邮箱、资料和既有账号。
本批控制方式、正常流程授权、生日容差及 App 验收要求：{batch_scope}。
接续阶段与实际错误：{last_observation_and_remaining_steps}。
按随附 skill 执行，只写本套原行，每项写后回读；保留实际提交密码。
结束报告平台结果、剩余项和关机回读；人工交接时说明设备仍开机。
随附材料：{current_skill_files_or_inline_content}。
```

“Full access”描述执行器配置，不能代替目标服务权限、网络规则或平台状态。交接写清本批已有授权，工具仍明确拒绝时报告其来源，不以新会话绕过明确的安全限制。

## 卡住的会话如何接手

先看最近操作、真实错误和设备状态。暂时没有 commentary、只读到 user message 或冷启动较慢，均不能单独证明死锁。

用户允许换会话时，先确认旧执行者停止操作并结束/移交，再给同一套资源创建新会话。新 Agent 先读取原四行、资料绑定和当前页面，再接续未完成阶段。保留历史会话 ID，读回新 turn 状态后转移拥有者。原会话仍在操作时不能双写或并行控制同一台手机。

发送后立即回读可能仍是旧的 completed turn。比较 turn ID 或开始时间与发送开始时间，直到看到新 turn，再判断是否启动失败；不要因旧结果误释放槽位。

## 按小时检查与最终回收

用户要求每小时检查时，记录下一次检查时间，在当前任务持续检查；只有工具和当前规则允许持久自动化、且用户已明确确认时才创建。区分实际创建的自动化与当前任务内计时，不能只写一个计划文件就声称定时器已生效。

每轮检查：活跃会话和归属、原行回填完整性、账号/资料是否串组、设备状态、实际受阻原因，以及尚未分配的任务。租约续期见接口参考；它只是设备生命周期协议，不代替业务进度检查。

最后逐套收齐原四行回读与关机证据，汇总成功和仍受阻结果。技术待处理不改名为成功，也不因为会话 completed 就说所有账号已注册成功。按用户约定结束本批监控；仍有人工交接时保留交接清单和设备归属。
